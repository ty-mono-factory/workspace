# Mini-factory 建设意向与下一步计划

## 1. 文档目的

本文记录 Mini-factory 的当前定位、建设边界、能力缺口和建议实施顺序，作为后续逐项讨论和实施的基础。

当前目标是在以下硬件约束内建设一套能够支持商业应用开发与交付的轻量基础设施：

- 约 1 TB 本地存储；
- 32 GB 内存；
- 硬件预算约 1,000 美元；
- 使用 Gitea 进行源码与基线管理；
- 使用容器化、离线物料和固定工具链控制构建环境；
- 逐步建立自动化测试；
- 使用外置存储介质进行基础备份与灾难恢复。

## 2. Mini-factory 的定位

Mini-factory 可以定义为：

> 面向个人或小团队、低并发、可离线构建、可追溯发布、可从冷备恢复的软件交付设备。

它不是云平台的缩小版，也不以大规模并发或高可用为首要目标。它的“工业化”体现在：

- 使用统一模板生产应用；
- 使用固定流程构建和测试；
- 每个发布制品都能追溯到源码、依赖和构建环境；
- 已经通过测试的制品可以被重复部署；
- 发布失败时可以回滚；
- 主机或硬盘损坏后可以按照文档恢复。

当前系统可以按三层理解：

```text
业务与接入层
Access Web + 业务应用 + Native C/C++ 能力
                ↓
平台工程层
Monorepo + 统一配置 + 数据库 + 日志 + 容器化构建
                ↓
连续性保障层
Gitea + 离线物料仓库 + 版本基线 + 制品保留 + 备份恢复
```

现有 `ty-demo-app` 的主要作用不是承载最终业务，而是作为验收载荷，证明以下链路能够贯通：

```text
登录与授权
→ Nuxt 页面和服务端 API
→ TypeScript
→ Node-API/C++
→ C 业务函数
→ 日志与数据库
→ 容器化构建和运行
```

## 3. 必须明确的系统边界

### 3.1 可以承诺的能力

- 为个人或小团队提供统一开发和交付环境；
- 支持低并发、可排队的自动构建；
- 在网络受限或断网条件下重建已准备好的项目；
- 保存源码、依赖物料、构建环境和发布制品；
- 对发布版本进行追溯、验证和回滚；
- 从离线备份恢复最近的稳定状态。

### 3.2 暂时不能承诺的能力

- 单机高可用；
- 零停机恢复；
- 大规模并行 CI；
- 跨机房容灾；
- 互联网规模的制品和日志存储；
- 在同一台机器上同时安全承担开发工厂和正式生产环境。

一台主机始终是一个故障域。外置 U 盘也只是灾备介质之一，不能单独构成完整灾备系统。

## 4. 建设能力与优先级

| 优先级 | 能力 | Mini-factory 的最低实现 |
| --- | --- | --- |
| P0 | 工厂输出标准 | 定义商业应用必须具备的目录、配置、日志、认证、健康检查、升级和诊断接口 |
| P0 | 可验证基线 | 每个发行版对应唯一 Git Commit、签名 Tag、锁文件、构建镜像 Digest、数据库版本、测试结果和制品校验值 |
| P0 | 自动质量闸门 | 未通过类型检查、测试、构建和冒烟测试的提交不能进入发布基线 |
| P0 | 制品管理 | 保存容器镜像、npm/Conan 包、离线安装包及其元数据；发布后不能静默覆盖 |
| P0 | 部署与回滚 | 使用同一个已测试制品从候选版提升为正式版，并支持回退到上一稳定版 |
| P0 | 恢复闭环 | 能在空白硬盘或另一台机器上，仅依靠灾备介质恢复关键系统 |
| P0 | Runner 隔离 | CI 任务不能读取 Gitea 数据、其他项目、宿主机密钥或任意控制宿主机 |
| P1 | 供应链证据 | 生成 SBOM、依赖漏洞报告、许可证清单、构建来源和制品签名 |
| P1 | 可观测性 | 监控磁盘、SMART、服务状态、备份新鲜度、CI 状态和证书有效期 |
| P2 | 第二故障域 | 增加独立 Runner、异地备份或可快速接管的备用主机 |

## 5. Gitea 的角色

Gitea 应作为 Mini-factory 的控制面，而不只是 Git 仓库：

```text
需求或 Issue
    ↓
Commit / Pull Request
    ↓
自动测试与人工审查
    ↓
受保护分支
    ↓
签名基线
    ↓
制品、SBOM、测试报告
    ↓
部署与回滚
```

需要逐步配置：

- 主分支禁止直接推送；
- Pull Request 必须通过指定状态检查；
- 新提交使旧批准失效；
- 管理员也遵守关键分支规则；
- 正式 Tag 和发布提交要求签名；
- 对工作流、构建文件和发布策略设置更严格的修改权限；
- 使用 Gitea Package Registry 保存 OCI 镜像、npm、Conan 和通用制品；
- 使用 Gitea Actions 驱动测试、构建、发布和周期性恢复验证。

参考资料：

- [Gitea 受保护分支](https://docs.gitea.com/1.25/usage/access-control/protected-branches)
- [Gitea Actions Runner](https://docs.gitea.com/usage/actions/act-runner)
- [Gitea Package Registry](https://docs.gitea.com/next/usage/packages/overview/)
- [Gitea 备份与恢复](https://docs.gitea.com/1.26/administration/backup-and-restore/)

## 6. 发布基线与制品出生证明

每次正式发布应生成一个机器可读的发布清单，例如 `release-manifest.json`，至少包含：

- 应用名称和语义化版本；
- Git Commit ID 和签名 Tag；
- 源码归档与锁文件的 Hash；
- Builder 镜像名称和不可变 Digest；
- Node、pnpm、编译器和 Native ABI 版本；
- 数据库 Schema 或 Migration 版本；
- 生产镜像、二进制和离线安装包的 SHA-256；
- 自动化测试结果；
- SBOM 文件及其 Hash；
- 发布日期和批准者；
- 上一个可回滚版本；
- 对应的安装、升级、回滚和恢复说明版本。

制品从候选环境提升到正式环境时不应重新构建。应提升同一个已经通过测试、具有固定 Digest 的制品。

## 7. 自动化测试策略

### 7.1 第一条黄金路径

优先打通一条能够覆盖系统核心边界的端到端测试：

```text
创建用户
→ 登录
→ 获得 Session
→ 访问受保护应用
→ 调用 Nuxt API
→ 进入 Node-API
→ 调用 C 函数
→ 校验返回值
→ 注销
→ 再次访问应被拒绝
```

### 7.2 分层测试

1. 快速闸门：ESM 检查、lint、typecheck 和单元测试。
2. 接口测试：配置、AccessContext、登录跳转、API 401 和禁用用户行为。
3. 数据测试：空库初始化、Migration、升级路径和数据兼容性。
4. Native 测试：边界长度、空值、Unicode、并发及 ASan/UBSan。
5. 浏览器 E2E：完成登录、进入应用、调用功能和注销。
6. 制品测试：启动生产镜像、检查健康状态和优雅退出。
7. 恢复测试：从备份恢复后重新执行黄金路径。

初期不以覆盖率数字作为主要目标。第一目标是保证任何破坏核心交付链路的变化都不能进入发布基线。

## 8. CI Runner 隔离

Runner 会执行仓库中的代码，应视为潜在的不可信执行环境。

最低要求：

- 最好使用独立机器；预算受限时，至少使用独立 VM 或严格隔离的容器；
- 限制 CPU、内存、磁盘和并发任务数；
- 初期只同时运行 1 至 2 个重型构建任务；
- 不挂载 Gitea 数据目录、宿主机密钥或其他项目目录；
- 不向普通构建任务暴露宿主机 Docker Socket；
- 外部或不可信 Pull Request 不得自动获得发布密钥；
- 每次任务使用临时工作目录，并在任务结束后清理；
- 缓存只能访问明确授权的目录；
- 签名任务与普通测试任务使用不同权限。

当前 `launch_builder.sh` 挂载了整个父级工作区，适合受信任开发者交互使用，不应直接作为 CI Runner 的安全模型。

## 9. 备份与灾难恢复

### 9.1 需要覆盖的数据

必须备份：

- Gitea 仓库、数据库、LFS、附件和配置；
- 业务数据库；
- 正式发布制品和发布清单；
- 基础设施代码与恢复文档；
- 必需的离线依赖与基础镜像；
- 加密后的密钥、签名材料和管理员恢复凭据。

可以重新生成，不必优先备份：

- `node_modules`；
- 临时构建目录；
- 普通编译缓存；
- 可以重新下载或重新生成的日志与中间产物。

### 9.2 介质策略

一个 U 盘不足以承担完整灾备。最低建议：

- 使用 A/B 两块介质轮换；
- 备份介质加密；
- 备份完成后物理断开；
- 至少一份备份不与主机处于同一地点；
- 每次备份生成文件清单和 SHA-256 校验值；
- 记录备份时间、来源版本、工具版本和恢复说明；
- 定期在空白环境执行真实恢复，而不是只检查备份文件是否存在。

Gitea 数据备份必须保证数据库一致性。使用 `gitea dump` 时应按照官方要求安排一致性窗口，不能简单复制正在写入的数据目录。

### 9.3 恢复目标

需要为系统定义：

- RPO：发生灾害时最多允许损失多少时间范围内的数据；
- RTO：主机或硬盘完全损坏后，多长时间内必须恢复服务。

灾备验收标准应是：

> 在原硬盘不可用且互联网断开的情况下，只依靠恢复文档和备份介质，在目标 RTO 内恢复 Gitea、源码、关键数据库、制品和最近稳定版本，并重新跑通黄金路径。

参考资料：

- [CISA StopRansomware Guide](https://www.cisa.gov/stopransomware/ransomware-guide)

## 10. 可观测性和日常运维

至少需要监控和告警：

- 主机 CPU、内存和负载；
- 磁盘容量、inode、SMART 和 I/O 错误；
- Gitea、数据库、Registry 和 Runner 的健康状态；
- 最后一次成功备份时间；
- 最后一次恢复演练时间；
- 自动化测试和发布流水线状态；
- TLS 证书到期时间；
- 日志异常增长；
- 离线物料和正式制品的完整性。

1 TB 存储需要明确的配额和保留策略，避免容器层、构建缓存、Actions 日志和历史制品耗尽空间。应保留足够空间用于一次完整构建、数据库临时文件和恢复操作。

硬件投入优先级建议为：

1. UPS 和自动安全关机；
2. 两块轮换使用的可靠外置备份介质；
3. 磁盘健康、容量和温度监控；
4. 后续增加一台低成本独立 Runner；
5. 出现真实内存瓶颈后再考虑从 32 GB 升级。

## 11. 当前仓库的主要缺口

1. `infra/docker/Dockerfile.production` 目前还是占位状态，尚未定义完整生产制品。
2. 当前生成器只能创建普通 TypeScript package，尚未形成应用、Native 模块、数据库迁移和 CI 工作流模板。
3. Native 单元测试和集成测试仍需补充。
4. 尚未形成正式的 Gitea Actions 工作流与基线准入规则。
5. 私有灾备脚本位于仓库之外，仓库内还需要一份不包含敏感信息的恢复接口契约。
6. 尚未看到正式制品的版本、保留、签名、晋级和回滚规则。
7. 当前 Builder 的工作区挂载方式不适合直接用于不可信 CI 任务。
8. 需要明确开发工厂与客户生产运行环境的分界。

## 12. 建议实施阶段

### 第一阶段：完成最小交付闭环

```text
提交
→ 自动检查和测试
→ 构建生产镜像
→ 生成发布清单
→ 保存正式制品
→ 外置介质备份
→ 空环境恢复
→ 黄金路径验证
```

这一阶段完成前，不建议引入 Kubernetes、分布式数据库或复杂微服务。

### 第二阶段：补充质量与供应链能力

- 增加完整的测试矩阵；
- 生成 SBOM；
- 执行依赖漏洞和许可证检查；
- 对正式制品和发布清单签名；
- 建立制品晋级、保留和回滚策略；
- 建立运行监控与容量告警。

参考资料：

- [NIST Secure Software Development Framework](https://csrc.nist.gov/pubs/sp/800/218/final)
- [NIST CI/CD 软件供应链安全指南](https://csrc.nist.gov/pubs/sp/800/204/d/final)
- [CISA SBOM Resources Library](https://www.cisa.gov/topics/cyber-threats-and-advisories/sbom/sbomresourceslibrary)

### 第三阶段：增加第二故障域

只有在真实吞吐量、客户需求或恢复指标要求时再增加：

- 独立 CI Runner；
- 异地自动复制；
- 备用构建主机；
- 更可靠的制品存储；
- 必要的服务冗余和高可用设计。

## 13. Mini-factory 的验收定义

Mini-factory 的第一版不以功能数量验收，而以以下结果验收：

- 任意正式制品都能追溯到源码、依赖、构建环境和测试结果；
- 同一发布基线可以在准备好的离线环境中重新构建；
- 未通过质量闸门的代码无法进入正式基线；
- 部署失败时可以回退到上一稳定制品；
- 主硬盘不可用后，可以只依靠灾备介质和文档恢复系统；
- 恢复完成后，登录、鉴权、Nuxt API 和 Native C 调用黄金路径全部通过；
- 日常运行能够及时发现磁盘不足、备份中断和基础服务故障。
